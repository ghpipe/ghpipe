# ghpipe 产品方案

> 这份文档只回答三件事：**我们做什么、用户能得到什么、业务流程怎么走**。技术实现见 [design.md](design.md)。

## 一句话

ghpipe 让 AI 编码助手在同一个仓库里，按「开发 → 独立验收 → 合并 → 收尾」的固定流程，把一个 GitHub Issue 自动做成已合并、可自证的代码。

## 我们在解决什么问题

| 现状 | 后果 |
|---|---|
| AI 写完就说完成，没有独立验收 | 自己批自己，质量靠运气 |
| 流程只写在提示词/文档里 | 约定挡不住越权：同一个 token 既能开发又能批准 |
| 进度散落在本地文件和聊天里 | 换工具、换机器就断线；"完成了"没有证据 |
| 环境依赖重（Python、gh、openssl…） | 装不起来、版本对不上，Windows 上直接跑不了 |

## 核心能力（卖点）

| 能力 | 用户看到的效果 | 靠什么保证 |
|---|---|---|
| **一个任务一条命令跑完** | 说一句"做 Issue 42"，主会话按流程推进到 done | 主会话只编排、不写代码；每一步都从 GitHub 读事实 |
| **开发和验收必须是两个独立 Agent** | "自己批自己"不可能发生 | 两个不同主体密钥 + 两个不同 GitHub App；验收绑定当前 commit SHA；合并要求"批准者 ≠ 所有开发主体" |
| **越权在工具层被拒绝** | 拿开发凭据去做合并，会被直接拒绝 | 签名会话 + 角色能力白名单 + 目标绑定（仓库/分支/PR/SHA） |
| **GitHub 就是账本** | 打开 Issue/PR 就能看到全过程，没有第二份状态 | 阶段标签、Review、Checks、合并提交、清理声明 |
| **done 是核验出来的，不是声称的** | 绿色 CI 不够，还要 main CI、元数据、分支清理都对上 | `status` 逐项核验；缺一项就是 `closing`，不叫完成 |
| **装完即用，三平台一致** | `npm install -g @ghpipe/cli` 一条命令；macOS / Linux / Windows 行为一致 | 单个静态二进制 + 技能内嵌，除 `git` 外无运行时依赖 |
| **换工具不丢线** | 换个 AI 工具或换台机器，按 `status` 就能接手 | 任务状态不落本地；本机绑定只有 仓库/Issue/分支/主体 |

## 业务流程

### 一、一次性接入（每个仓库只做一次）

```text
安装 CLI（npm 一条命令）
   │
   ├─ 创建/安装 GitHub App ── 一次浏览器会话、两次点击（GitHub 不支持无浏览器创建，见设计 §11.1）
   ├─ 写项目配置 ── 原生命令、必需检查、App 绑定、默认分支
   ├─ 装技能 ── 生成 AGENTS.md 入口 + 把技能放进各 AI 工具能读到的位置
   └─ doctor 校验 ── 两个角色凭据、仓库访问、规则就绪
```

### 二、每个任务的交付循环（这是产品的核心）

```text
【正常路径】
ready ──主会话领取──▶ active ──开发/测试/开 PR──▶ review ──独立验收通过──▶ 合并（squash）
                                                                            │
                                                                            ▼
                                    自动清理分支 ──▶ 核验 main CI / 元数据 / 分支已清
                                                                            │
                                                                            ▼
                                                              done ──▶ 释放任务 ──▶ 下一个

【返修路径】
review ──要求返修──▶ changes-requested ──Developer 修复──▶ review
                                    新 SHA 必须重新签发授权、重新验收
```

阶段含义（阶段是从 GitHub 事实算出来的，不是手工改的状态）：

| 阶段 | 事实 | 下一责任人 |
|---|---|---|
| `ready` | 有 Issue，还没有分支/PR | 主会话领取 |
| `active` | 分支或 Draft PR 存在 | Developer |
| `review` | 非 Draft PR，未合并 | Reviewer |
| `changes-requested` | 独立验收要求返修 | 原 Developer |
| `closing` | 已合并，但 main CI / 元数据 / 清理未确认 | 主会话收尾 |
| `done` | 全部核验通过 | 结束，不再改动 |
| `cancelled` | Issue 与 PR 关闭且未合并 | 报告取消，保留分支 |

### 三、三类角色，边界写死在工具里

| 角色 | 能做什么 | 绝不能做 |
|---|---|---|
| **主会话（Orchestrator）** | 读事实、领取任务、派发、安排验收、合并、收尾、释放任务 | 写代码、提交、代替验收、借用别人身份 |
| **Developer** | 原地实现、跑测试、提交、推送、开 PR | 验收、合并、领取下一个任务 |
| **Reviewer** | 对固定 SHA 独立验收、批准或要求返修 | 改代码、推送、合并 |
| **Owner（人）** | 建立信任、签发会话、配置仓库规则、发布放行 | 替开发、替验收 |
| **automation（CI）** | 只读 + 元数据同步 | 任何交付写入 |

### 四、异常怎么走

| 情况 | 处理 |
|---|---|
| 写操作结果不确定（网络中断、超时） | **不重放**；原主体回读远端证据确认后才继续 |
| 验收不通过 | 回原 Developer 修复；**新提交必须重新签发授权、重新验收** |
| 换人 / 换工具 / 换机器 | 换的是"主体"，不换角色；交接前必须确认旧执行者已停止写入 |
| 任务取消 | 要求 Issue 与所有 PR 关闭且未合并，保留分支与提交，不当作完成 |
| 门禁/规则不明 | 停下来报告，不用 admin/bypass 绕过 |

## 对开发工具的要求（能力探测与降级阶梯）

ghpipe 最核心的承诺是「开发与验收必须是两个独立 agent」。主流的开发工具（Codex、Claude Code、OpenCode 等）都提供子 agent 能力，但**形态不同、投递方式不同**，所以 ghpipe 不靠"听说支持"来判定，而是**先探测、再据实选择通道**：

- **探测**：派两个子 agent，各持一个互不可见的随机令牌并回报（外加一个谁也不给的对照令牌）。三项全过才算合格：任务能投递、上下文互相独立（互相报不出对方令牌）、主会话能收到两份结果。
- **按结果处置**：不合格时区分原因——工具没有派发能力、任务投递失败、上下文被共享、结果收集不到、无法限制验收者写权限——每种原因都有对应的处置（换通道、换会话形态、或要求人工派发），并写进账本。
- **按工具选通道**：Codex 用派发任务文本（或自定义 agent 指令）、Claude Code 用 subagent 定义文件与 description、OpenCode 用配置与 `@` 点名；任何情况下任务正文都在 Issue 或工作区文件里留一份，子 agent 先读它再开工。
- **不降级的原则**：无论哪种形态，**主会话都不会自己开发、自己验收**；需要降级时（独立会话、人工派发）必须显式记录独立性来源，绝不把它说成原生子 agent。

## 使用场景

| 场景 | 怎么用 |
|---|---|
| **单人 + 一个 AI 工具** | 开发与验收跑在两个独立上下文（两个会话/两个工具），凭据各自独立 |
| **团队 / 多工具** | 开发用 Codex，验收用别的工具或另一个人；两个 GitHub App 或两个账号隔离 |
| **无人值守** | 批次放行后主会话连续跑多个 Issue；元数据同步、质量门禁、发布、每日升级检查交给 GitHub Actions |

## 缺陷从哪来

三个入口，最后都汇入同一条生命周期：

| 来源 | 谁提交 | 怎么进系统 |
|---|---|---|
| **用户**（产品使用者） | 外部用户，没有仓库写权限 | 填 GitHub 上的结构化表单（由 ghpipe 生成）：现象、复现、环境、影响、证据。提交后进"待分诊" |
| **内部** | 开发、验收、主会话 | 直接生成缺陷任务（开发/验收发现超范围缺陷时先写草稿，由主会话归档） |
| **工具自身错误** | ghpipe 自己（需显式开启） | 把脱敏后的固定字段上报到工具仓库，帮工具方修工具 |

**用户提交的报告不是任务，必须分诊**：工具会先检查"必填信息齐不齐、能不能复现、是否重复、是否在支持范围"，然后由 Owner 决定**接受**（补上严重度与里程碑，变成可领取的缺陷任务）或**拒绝**（重复/超范围/信息不足，并列出还需要补什么）。用户原文不会被改写，工具只在末尾追加结构化的受管段落。

**"项目自动提 bug 到工具仓库"默认关闭**，开启需要你显式配置一个**专用凭据**（只对工具仓库有 Issues 写权限，绝不复用业务项目的角色凭据），并且发送前可以用 `report preview` 看到将要发送的确切内容。发送内容只有固定白名单字段（版本、动作类型、错误分类、脱敏端点模板、内部模块与行号、平台），不含项目名、命令参数、正文、日志、环境变量或任何凭据。

## 缺陷怎么走（和开发切片有什么不同）

任务分三类，走同一条生命周期，但**必填信息和验收证据不同**：交付切片（`slice`）验收"方案里的条件是否满足"；缺陷（`bug`）验收"修复前能复现、修复后不再复现"；维护（`maintenance`）只需一段说明。

**一个缺陷必须说清五件事**（对应模板 `templates/bug.md` 的必填段）：

1. **现象**：预期是什么、实际是什么。
2. **复现**：环境（版本/平台/commit）、步骤、最小复现命令、稳定性（必现或偶现 + 概率）。
3. **影响**：受影响用户或功能、数据与安全影响、首次出现的版本/提交、是否回归。
4. **证据**：脱敏后的日志、报错、截图或 CI 链接。
5. **修复验收**：修复后可观察的行为、回归测试要求、不包含范围（明确禁止顺手重构）。

**缺陷的验收比切片多一条硬要求**：新增的测试必须"修复前失败、修复后通过"。这件事不靠人凭感觉判断——工具在临时工作区里用"旧实现 + 新测试"跑一次（应当失败），再用完整修复跑一次（应当通过），把两次结果作为验收证据。无法稳定复现的偶发缺陷走显式例外：标注"偶现"、给出已有证据、加针对性测试或防护性断言，并由验收者明确写明"无法证明回归覆盖"。

**严重度决定要不要插队**：

| 严重度 | 流程 |
|---|---|
| blocker（线上不可用 / 数据损坏 / 凭据泄露） | 紧急修复：单独里程碑，绕过批次放行直接领取；独立验收与必需检查一样不能少 |
| critical（核心功能不可用、无绕过） | 需 Owner 批准插入当前或下一个里程碑 |
| major / minor | 正常批次排期 |

**谁能登记缺陷**：Owner 或主会话归档；开发或验收过程中发现、但超出当前任务范围的缺陷，先写成待归档草稿并在原 Issue 留痕，由主会话归档——不给开发角色扩权。

## 人还需要做什么

目标是把人工降到只剩真正需要人判断的地方：

| 场景 | 人的操作 |
|---|---|
| 首次接入 | 浏览器里两次点击（创建 App、安装），其余 CLI 自动完成 |
| 签发角色授权 | 一条命令（自动绑定 PR 与当前 SHA） |
| 决定做什么 | 放行批次、或指定一个 Issue |
| 例外判断 | 返修超限、范围变更、门禁不明 |

领取任务、开发、独立验收、合并、清理分支、同步标签、升级 CLI 与技能——**全部自动**。

## 我们不做什么

- 不启动模型、不做模型路由，不绑定任何特定 AI 工具或客户端
- 不提供常驻服务、不建任务数据库、不做第二套状态
- 不托管代码，不替代 GitHub 对分支保护、必需检查、审批人数的裁决
- 不做跨仓库原子操作、不做跨机器分布式锁

## 安全：我们承诺什么、不承诺什么

采用**单机单用户**部署（不使用独立容器或独立 OS 用户）。这意味着任何以该用户身份运行的程序都能读到该用户可读的文件，所以"阻止同用户进程读取明文凭据"这种事**做不到**，我们不承诺。我们承诺的是三件能真正做到的事：

| 承诺 | 具体表现 |
|---|---|
| **越权和误用会被拒绝** | 拿开发授权做验收/合并、跨任务操作、超出角色的能力，命令直接失败并说明原因 |
| **把凭据暴露面压到最小** | 验收/合并用的凭据按需签发、用完即弃（默认不写盘）；会话按任务短时有效、写操作只允许一次 |
| **越界使用可查** | 谁签发的、谁用的、绑定哪个 Issue/PR/SHA 都记在账本与本地日志里，`doctor` 直接列出当前哪些凭据在盘上 |

不承诺的部分（同样是产品边界）：

- 不阻止同用户进程读取磁盘上的凭据文件——我们**不做加密、不接生物识别**，因为同用户下那只是提高门槛而不是边界；实际收益来自"少落盘 + 短有效期 + 可审计"，以及 GitHub 侧的权限天花板（偷到开发凭据也进不了主分支、写不了 Issue）。
- 不阻止有人替换 CLI 或绕过它直接调用 GitHub API——这是任何同用户程序都有的能力。

一句话：**我们用"拒绝越权 + 凭据尽量不落地 + 权限天花板 + 全程留痕"替代容器隔离**，并且把做不到的部分明确写出来，而不是假装安全。

## 和替代方案的差别

| 替代方案 | 缺什么 |
|---|---|
| 让 Agent 自由发挥 | 流程不可复现、无法审计、容易自审自过 |
| 只写一份 AGENTS.md/提示词约定 | 约定没有强制力，越权照样发生 |
| 上一版 aipipe | 需要 Python + gh + openssl；技能靠手装/软链接；Windows 跑不了 |
| SaaS 流水线 / 云端 Agent | 代码托管给第三方；无法在你自己的机器与仓库上闭环 |

## 从零开始：还没有代码和测试时怎么走

常见情形：项目刚接入，接下来要做的是设计文档、开发方案、切片计划——没有源码、没有测试脚本，业务 CI 跑不起来。我们的处理是**门禁随范围收紧，而不是一刀切要测试**：

| 阶段 | 必需检查做什么 | 需要业务测试吗 |
|---|---|---|
| **接入（bootstrap）** | 校验配置合法、变更范围合法（文档/配置/工作流）、质量工作流结构完整 | **不需要** |
| **第一个业务切片（strict）** | 业务变更必须跑真实测试；缺测试命令、测试失败、检出不干净都失败 | 需要 |

要点：

- **必需检查只有一个名字**（`ghpipe-quality`），从第一天装好就不再变，只是策略随改动范围收紧——所以不会出现"新检查还没成功过就没法装成必需检查"的死锁。
- **文档与方案走 bootstrap 范围**：`docs/**` 这类改动只做文档级校验，能正常合并到主分支；独立验收依然要求（验收的是方案内容，不是测试结果）。
- **进入 strict 的时机**是第一个业务切片：那次 PR 必须同时交付实现、有效测试和登记好的测试命令。
- **不制造假检查**：不允许用"永远通过"的脚本冒充门禁，也不允许路径过滤让必需检查不产生（那会让 PR 永远合并不了）。

## 最小可用路径

```bash
npm install -g @ghpipe/cli        # 1. 安装
ghpipe init repo --apply          # 2. 接入当前仓库（引导创建/安装 App、写配置、装技能）
ghpipe doctor --for handoff       # 3. 校验就绪
```

然后在仓库里说一句「做 Issue 42」，主会话就会按上面的循环跑到 `done`。

## 复杂度分层

为了避免"功能很多但不知道从哪用起"，能力分三层，**核心层先做完就能用**：

| 层 | 内容 |
|---|---|
| **核心（必须先有）** | 单任务交付循环（领取 → 开发 → 独立验收 → 合并 → 清理 → done）、角色隔离与签名授权、技能分发、CLI 三平台可用 |
| **增强（用完核心再加）** | 批次发布与放行、元数据自动同步工作流、质量门禁模板、`ghpipe update` 自更新 |
| **可选（按需）** | 技能聚合布局（suite）、不用 App 的凭据模式、共享 App 信任、32 位构建目标、产物来源证明 |

## 怎么算成功

1. 一个任务从 `ready` 到 `done`，人只需要说一次"做这个"。
2. 任何一个 `done` 都能只用 GitHub 上的事实自证，不需要解释。
3. 换一个 AI 工具或换一台机器，能无缝接着做。
4. 安装只要一条命令，macOS / Linux / Windows 上表现一致。

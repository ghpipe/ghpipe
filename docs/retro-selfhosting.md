# 复盘：第一次自举（用本工具开发 ghpipe 自身）

时间：2026-09-13。范围：Issue #1–#7 的开发/验收流程，以及期间关于"宿主是否支持原生子 agent"的误判。

## 1. 事实时间线

| 时间点 | 发生了什么 |
|---|---|
| 起点 | 用户要求：开发与验收用**独立 agent**，主会话只做调度与合并 |
| 第一次尝试 | 用 `spawn_agent` 派发 Developer；子 agent 回报"没有收到任务正文（只有环境）" |
| 替代通道 | 改用 `codex exec` 起独立进程充当 Developer / Reviewer，完成 Issue #1/#2/#3/#4（独立进程确实是独立上下文，但不是原生子 agent） |
| 用户质疑 | "为什么不用独立的子 agent" → 再次尝试原生派发，再次出现"没有任务正文"；子 agent 还自行派生了两个下级 agent、改动了分支 |
| 误判 | 我把"派发消息没送达"上升为"工具不支持原生子 agent"，写进 design §6.8、product.md、handoff.md，并建议换工具 |
| 用户纠正 | "当前开发工具支持原生子 agent"，要求把这个判断设计清楚并参考主流实现 |
| 修正 | 查官方文档（Codex / Claude Code / OpenCode）→ 把 §6.8 重写为**能力阶梯 + 三 nonce 探针 + 失败分类 + 派发通道**；product.md、handoff.md 同步 |
| 实测 | `fork_turns:none` + 消息 → 子 agent 明确"消息里没有任务"；改为默认继承上下文 → 子 agent 自行读到仓库与交接文档，**并开始实现 Issue #7**（工作区出现 `internal/metadata/`） |

## 2. 根因

| # | 根因 | 说明 |
|---|---|---|
| R1 | **把通道问题当成能力问题** | 只有两个失败样本，且都发生在"不继承上下文、只靠消息字段投递"的用法下。我没有隔离变量（消息通道 vs 上下文继承 vs 工具能力）就下了工具级结论 |
| R2 | **结论过快写进契约** | 把一次观察当成产品要求写进 design/product/handoff，等于把错误信念固化成规范；正确做法是先记为"未验证假设"，用探针取证后再落设计 |
| R3 | **派发方式本身用错** | 用 `fork_turns: "none"` 派发却不给子 agent 任何可读的任务来源：消息字段在本环境不投递 → 子 agent 只能猜 |
| R4 | **缺少失败分类** | 没有区分"没有派发能力"与"派发成功但任务没送达"，所有症状都塌缩成"不支持" |
| R5 | **子 agent 角色边界没写清** | 继承上下文后子 agent 会按自己的理解行动：自行派生下级 agent、改动分支，甚至挟持了调度者尚未推送的提交（清理时被安全校验拦下） |
| R6 | **降级没留痕** | 用 `codex exec` 独立进程完成 Issue #1–#4 时，没有按"独立性来源"标注（`separate_session`），事后才补 |

## 3. 影响

- 直接损失：一轮无效往返（探索"换工具"），并让设计文档与产品文档在短时间内带上一条错误结论。
- 隐性风险：子 agent 自行派生与改分支，差点让一份未推送的文档提交被删除（安全校验拦住，已 cherry-pick 回 main）。
- 正面产出：暴露了"宿主能力判定"这个此前没有设计的空白，促成了 §6.8 的完整设计（阶梯 / 探针 / 分类 / 通道 / 降级留痕）。

## 4. 已修正

1. `design.md §6.8` 重写：能力阶梯 L0–L3（对齐 Codex「subagent workflows 默认启用 + 自定义 agent」、Claude Code「subagents / background agents / cross-session messaging」、OpenCode「primary agents + subagents」）；三项必须属性 A1 任务投递 / A2 上下文独立 / A3 结果可收集，两项加分 A4 独立主体 / A5 可限工具集。
2. 判定方法（**设计已写，尚未实现**）：声明（先验，不作证据）→ **三 nonce 探针**（A 拿 `N_A`、B 拿 `N_B`、对照 `N_X` 谁都不给；**必须先派 B 再派 A**，否则 A2 会假通过）→ 证据落 `.ghpipe/state/host-probe.json` + Issue 评论（**Issue 评论是权威，本地 JSON 只是缓存**）；`doctor` 状态机 `unprobed / compatible / incompatible` 与 `--probe-host` 见 G48，目前尚未落地。
3. **失败分类与处置**：`no_dispatch` / `no_task_delivery` / `shared_context` / `no_collect` / `restricted_absent`，每类给出可执行补救（换通道、换形态、结果走账本、CLI 侧补偿）。
4. 降级阶梯与留痕：原生子 agent → 独立会话/进程（`separate_session`）→ 人工派发（`manual_dispatch`）；**禁止 `self_review`**。
5. 派发通道优先级：工具原生派发 → 任务文件（`docs/TASK.md`，子 agent 先读）→ 账本（Issue/PR 正文与评论）。
6. `product.md`、`handoff.md` 删掉"本工具不兼容"的说法，改为"先探测、按结果处置"；`handoff.md` 标题与 `product.md` 小节标题去掉"换工具/硬性前置"的残留措辞。

## 5. 待验证（不要把推断当结论）

| 项 | 状态 | 怎么验证 |
|---|---|---|
| A2 上下文独立 | **工具能力成立，但本环境链路不成立** | 独立上下文子 agent 能派发、能回报（A2/A3 成立）；但子 agent 沙箱**无网络**、读不到 Issue，派发消息也不投递正文 → "任务只来自 Issue"无法满足，按 `no_task_delivery` 走降级 |
| A5 可限工具体 | 未测 | 是否能把 Reviewer 子 agent 的工具集限制为只读（Claude Code 有该能力；本工具待测） |
| 任务文件通道 | **已废弃（违反唯一载体）** | 曾用 `docs/TASK.md` 作过渡通道，但它造出第二份任务真相，与「Issue 是唯一载体」冲突；已删除并写进 design §6.8.5 的禁止项 |
| 子 agent 的网络访问 | 已知受限 | 子 agent 沙箱内无网络（`gh`/`api.github.com` 不可达）→ 调度者必须把 Issue 正文落到工作区文件，不能假设子 agent 能自己读 Issue |
| 通道矩阵（单变量） | 未跑 | 必须逐格只改一个变量：`fork_turns:none` + 仅消息（已知失败）／`fork_turns:none` + 简报文件／继承上下文 + 简报文件；此前"一次改两个变量"的实测不算证据（评审指出） |

## 6. 下次的行动清单

1. **派发前**：先跑三 nonce 探针并分类；把结论写成 Issue 评论（工具、级别、失败分类、时间）。
2. **派发前**：把任务正文写进 `docs/TASK.md`（与 Issue 正文一致），并在其中写明角色、范围、验收条件、硬约束、汇报格式，以及**禁止事项**：不得派生下级 agent、不得切换或删除分支、不得 commit/push（由调度者代提交）。
3. **派发前**：调度者先把自己手上的改动提交并推送，避免子 agent 的临时分支挟持未推送提交（本次差点发生）。
4. **验收**：必须是**另一个**子 agent，在**固定 SHA** 上独立核验，含证伪尝试（变异/对抗输入），且不得改动代码。
5. **文档纪律**：设计文档里严格区分「已实测」「推断」「未验证」；任何"不兼容/降级"的结论必须附探针证据，否则只作为假设记录。
6. **留痕纪律**：降级（独立会话/人工派发）必须写进 `execution log` 与 Issue 评论，且不得表述为原生子 agent。
